# Contributing

Thank you for helping make PM Interview OS more practical, clear and inclusive.

## What makes a useful contribution?
A strong contribution helps a reader take an action and understand whether they did it well. Good contributions include original interview questions, worked case studies, answer canvases, realistic mock interviews, clearer explanations, accessible examples, corrections and sourced updates.

## Before opening a pull request
1. Search existing modules to avoid duplicates.
2. Read [QUESTION-WRITING-STANDARD.md](QUESTION-WRITING-STANDARD.md).
3. Use the closest existing template and preserve the folder conventions.
4. Use plain, direct language. Explain acronyms on first use.
5. Label fictional data and assumptions clearly.
6. Cite public sources for factual, current or company-specific claims.
7. Never include confidential interview questions, private candidate information, copyrighted paid course material or proprietary company documents.

## Question contribution checklist
- [ ] The question tests a clearly named competency.
- [ ] The candidate knows the expected time and difficulty.
- [ ] The prompt includes enough context to start.
- [ ] The guide explains an approach, not a memorised script.
- [ ] Follow-up questions test depth and trade-offs.
- [ ] Common weak patterns are explained constructively.
- [ ] Any sample data is labelled fictional or cited.
- [ ] The answer can be evaluated with observable evidence.

## Case study checklist
Include a context, objective, constraints, data, candidate tasks, suggested analysis, possible options, trade-offs, metrics, risks, and evaluation rubric. State that more than one solution can be defensible.

## Writing conventions
- Use descriptive headings and meaningful links.
- Prefer tables for comparisons, not for long paragraphs.
- Use inclusive examples across geographies, industries and career stages.
- Avoid claiming that one framework is universally correct.
- Do not guarantee hiring outcomes.
- Keep answers self-contained so a reader can use a file without needing an external course.

## Pull request process
1. Explain the user problem the change addresses.
2. List the files changed.
3. Describe how you checked accuracy and links.
4. Note any assumptions, sources or limitations.
5. Request review when the contribution is ready.

Maintainers may request revisions to improve clarity, originality, accuracy, accessibility or consistency.
